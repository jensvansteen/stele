# Changelog

## 0.1.0-rc.6 — Release candidate

- **Targets: one specification, several places that prove it.** Targets are optional; without them nothing changes. A project declares its targets in `stele.config.json` (`"targets": { "ios": { "paths": ["ios/**"] }, … }`, with an optional `"evidenceOnly": true` for an end-to-end suite), and a specification opts in on its first line: `<!-- stele: spec v1; targets: ios, android -->`. `targets` is the first field that format version 1 defines; other fields still warn with `SPEC_ANNOTATION_FIELD_IGNORED`. See the new [Targets](https://jensvansteen.github.io/stele/guide/targets) guide, with worked examples for replicas, a split front end and API, iOS and Android, and a `system` journey.
- A requirement or scenario narrows its targets with a `Targets: a, b` line next to its `Verification-ID:`. It may only narrow. The line is metadata: it never enters the text, the steps, or an approval digest.
- Plan entries of a targeted scenario carry a `target`, and their evidence IDs put it between the scenario and the level: `<scenario>.<target>.<level>[.<n>]`, such as `scn.share.3c4d5e6f7a8b.ios.unit`. Every target a scenario applies to needs its own evidence. The TypeScript and Go anchor scanners read targeted IDs, and the folders of every target's `paths` are scanned for anchors and fingerprinted as inputs.
- New diagnostics: `SPEC_TARGETS_MALFORMED`, `SPEC_TARGET_UNKNOWN`, `SPEC_TARGETS_WIDENED`, `SPEC_TARGETS_MISPLACED`, `SPEC_TARGETS_UNDECLARED`, `SPEC_TARGETS_MISMATCH`, `SPEC_TARGETS_CHANGE_UNCOVERED`, `PLAN_TARGET_NOT_APPLICABLE`, `ANCHOR_TARGET_OUTSIDE_PATHS`, and `LINK_TARGET_IMPLEMENTATION_MISSING`, each with its meaning and fix in the catalogue. `PLAN_EVIDENCE_MISSING` names the target that lacks evidence, and `PLAN_EVIDENCE_INVALID` covers a missing or mismatched `target`.
- The human report shows a target matrix (a row per capability with passed and applicable scenarios per target, and up to ten scenario rows with a gap), and the verification report adds `targets` verdicts per target and `evidenceTarget` on test links. The link index adds `targets`, the file `targets`, `declaredTargets` and `applicableTargets` per item, `target` on evidence entries and anchors, and a `matrix` per scope. Every new field appears only when a scope has targeted specifications.
- Added `--target NAME`, repeatable, to `test`, `verify`, `validate`, `check`, and `index`, for example one CI job per target: `npx stele check --all --target android`. Specifications without targets describe the whole project and stay in scope. An unknown target, or `--target` in a project without targets, exits with code `2`.
- `stele ids` and `stele annotate --change` copy a capability's `targets` into a new delta spec's annotation. Added `stele annotate --specs --targets-from <archived-change-dir>`, which restores targets after `openspec archive`; the `stele-archive` skill and the archive guidance that `stele init` merges into `openspec/config.yaml` now run it, replacing the earlier `stele annotate --specs` entry.
- The `stele-plan` skill explains where behavior and testing differences between targets belong, the targeted evidence ID form, and the replica, split, and journey patterns.
- The positional arguments of `stele test` are now called selections in the help text, messages (`unknown test selection`), and documentation.
- **Compatibility:** a project without targets produces the same output as 0.1.0-rc.5, byte for byte, and keeps its plans and approvals; an end-to-end test compares the two. **Targeted projects need this release:** 0.1.0-rc.5 and older warn about the `targets` field and read `@verifies scn.x.ios.unit` as a bare scenario anchor.

## 0.1.0-rc.5 — Release candidate

- Added `--annotations=auto|github|never` to `validate`, `verify`, `test`, and `check`. In GitHub Actions (`GITHUB_ACTIONS=true`), Stele writes each finding the report shows and each failed test as an `::error` or `::warning` workflow command to standard error, so they appear inline on the pull request diff. Truncated groups add one annotation that counts the rest, and `--details` annotates every finding. Paths are relative to `GITHUB_WORKSPACE`. `stele check` also annotates missing Verification-IDs and specification files without a valid annotation. Standard output, JSON, report and evidence files, and exit codes are unchanged; `--annotations=never` turns annotations off. Any other value exits with code `2`.
- Added the [Continuous integration](https://jensvansteen.github.io/stele/guide/continuous-integration) guide with a ready-to-copy GitHub Actions workflow that runs `npx stele check --all`, and notes on exit codes, output, pinning, browser e2e evidence, and merging changes complete.
- Stele's own CI now also runs `stele check --all` with the Stele built from the pull request, so every active change must be approved, implemented, and passing before it merges.
- **Faster test runs:** `stele test`, `validate`, and `check` start one test process per batch instead of one per test: the selected tests of one Go package and build tag set run in one `go test -json -count=1 -run '^(A|B|…)$'`, and those of one Node file in one `node --test --test-name-pattern='^(a|b|…)$'`. Batches still run one at a time. On this repository a warm `validate --specs` drops from about 95 s to about 30 s. No flags or configuration change.
- Each test's outcome still comes from its own result in the batch output. A passed test stays passed even when another test of its batch fails. Evidence schema 3, report files, and `--json` output are unchanged, and identical to one process per test for tests that do not crash.
- **Behavior change:** tests of one batch share their process, as under `go test ./pkg` and `node --test file`, so package-level state, `TestMain`, `init`, and Node module state are shared. A test that only passes alone in its process may now fail.
- **Crashed batches:** a batch that does not report the end of its run (a crash, `os.Exit`, `process.exit`, a build failure, or a kill) fails its tests without a result with `test-process-failed`; tests that already had a result keep it. Progress prints `INCOMPLETE <batch> did not complete (exit status N)`, and the report lists the batch, its exit status, and its last output lines under "Incomplete test processes". Process output never reaches evidence.
- **Node skipped tests** (`# SKIP`) now fail with reason `test-skipped`, as Go skipped tests already do, instead of `test-not-executed`.
- Progress reports each test as soon as the batch output shows its result, so failures still appear before their batch ends; on a terminal the progress line names the running batch.
- Added `stele lsp`, a Language Server Protocol server over standard input and output in the same binary, for VS Code, Zed, JetBrains IDEs, Neovim, Helix, and any other LSP client. It serves every scope of each workspace folder, like `--all`, and names itself `stele` with the version `stele --version` prints. See the new [Editor integration](https://jensvansteen.github.io/stele/guide/editors) guide.
- Hover on an `@implements` or `@verifies` anchor shows the requirement's text or the scenario's `WHEN`/`THEN`/`AND` steps as a card, per scope, with the evidence level, approval, and last outcome (marked stale). Hover on a requirement or scenario heading lists where it is implemented and tested.
- Go to definition works both ways (anchor to heading; requirement heading to `@implements`; scenario heading to `@verifies`), and find references lists every implementation and test of a behavior, optionally with its headings.
- CodeLens shows a status on requirement and scenario headings, such as `unit ✓ · e2e ✗ · stale`, combined with the rule of the execution verdict, with run actions (`▶ Run all` and one per level), and on every anchor a summary of the linked behavior that opens its specification; test anchors also get `▶ Run` for their own evidence entry.
- `stele.runTests` runs tests from the editor through the same runner, batches, and evidence merge as `stele test <targets...>`, with `$/progress` per finished test and per batch that did not complete, one run per project, and a result with each outcome, the incomplete batches, and the scope's verdicts. Cancelling sends `SIGTERM` to the running batch's process group, then `SIGKILL` after about 2 seconds, writes no evidence, and ends the command with `RequestCancelled`. `stele test` itself is unchanged.
- Diagnostics in the editor are the findings `stele verify` reports for every scope, with the same codes and severities and the catalogue's meaning and fix, except `PLAN_UNAPPROVED`. A change is checked at the implementation stage once its plan has an approved entry. Two codes that only the editor reports join the catalogue: `EXECUTION_FAILED` and `EXECUTION_STALE`.
- An "Add Stele annotation" quick fix writes exactly the bytes `stele annotate` writes, with a command fallback for clients without code action literals.
- A custom `stele/index` request returns the document `stele index --json --all` prints, byte for byte.
- Evidence, report, index, and plan files are now written atomically (a temporary file, then a rename), so a reader never sees a partly written file. Their bytes are unchanged.

## 0.1.0-rc.4 — Release candidate

- Stele is now released under the MIT License: the repository has a `LICENSE` file, and the npm package declares `"license": "MIT"` and ships the license text.
- Added the Stele specification annotation, `<!-- stele: spec v1 -->` on the first line of a specification file, so Stele and editors can recognize Stele specifications and their format version. Whitespace, CRLF, and a byte order mark are tolerated, and `; key: value` fields are ignored with a warning in version 1. See the new [Specification format](https://jensvansteen.github.io/stele/concepts/spec-format) page.
- Verification reports `SPEC_ANNOTATION_MISSING`, `SPEC_ANNOTATION_MISPLACED`, `SPEC_ANNOTATION_MALFORMED`, `SPEC_ANNOTATION_UNSUPPORTED`, and `SPEC_ANNOTATION_FIELD_IGNORED`. Unannotated files are still read and verified.
- Added `unannotatedSpecs` to `stele.config.json`: `warn` (the default in 0.1.x) or `error`. **In 0.2.0 the default becomes `error`**; `warn` stays accepted as an explicit choice. Any other value exits with code `2`.
- Added `stele annotate [--change ID | --specs | --all] [--check] [--json]`, which adds the annotation to every file of a scope that lacks one, preserves every other byte, and never edits a misplaced, malformed, or unsupported annotation.
- `stele ids` adds the annotation to delta specs together with missing IDs, and `stele init` annotates the current specifications and the delta specs of active changes. The `stele` schema's specification template starts with the annotation.
- The `stele-archive` skill runs `stele annotate --specs` after archiving and before `stele validate --specs`, because OpenSpec drops the annotation when it creates a new current specification. The archive guidance that `stele init` merges into `openspec/config.yaml` names the same step and replaces the earlier entry.
- Additive JSON: `stele ids --json` gains `annotations`, and the link index gains `specFiles` and a `specVersion` on requirements and scenarios, within schema version 1.
- **Migration:** after upgrading, run `npx stele init` or `npx stele annotate --all`, then set `"unannotatedSpecs": "error"` to adopt the 0.2.0 behavior early.
- **Human output changed:** `validate`, `verify`, and `test` print a report with a header (version, command, scope), a per-capability overview, one check line per stage (OpenSpec strict validation, Specifications, Plan approval, Linkage (anchors), and Test execution with counts by level and the duration), errors and warnings grouped by diagnostic code with their meaning, a `→ Fix:` step, and the first five findings with `file:line`, failed and stale tests by name, and one verdict line. Plan approval problems no longer read as "implementation verification fail". `validate` now shows warnings such as `PLAN_V1_DEPRECATED`. With `--all`, a summary lists every scope's verdict. Scripts should use the exit code and `--json`; the JSON output is unchanged.
- Live progress on standard error while commands run: on a terminal one line updated in place with the test counter, the current scenario and level, pass and fail counts, and elapsed time, with failures printed as they happen; without a terminal, plain lines per stage, per finished test file, and per failed test, without escape sequences. `validate` runs OpenSpec strict validation and a plan and linkage check before the tests, so their problems show early.
- Added `--details` (no truncation), `--quiet` (verdict line only, no progress), and `--color=auto|always|never` to `validate`, `verify`, `test`, and `check`. `auto` respects `NO_COLOR` and `TERM=dumb`.
- Added `stele check [--change ID | --specs | --all]`, one CI gate that runs the ID check, the annotation check, and `stele validate`, prints one combined summary, and exits with the worst code (`2` over `1` over `0`). The `stele-verify` skill recommends it.
- `stele --version`, the help text, the report header, and `verifier.version` now show the npm package version, such as `0.1.0-rc.4`, set at build time from `package.json`. They showed `0.1.0` before.
- Combining archived plans for `--specs` now prefers, for each ID, the archived change whose delta spec has the current text of the specification, then the archive date and the change name. Changes archived on the same day no longer combine in alphabetical order. A new `PLAN_ARCHIVE_ORDER_AMBIGUOUS` warning names two same-day plans that still disagree.
- Requirements under `## REMOVED Requirements`, as headers or bullets, are no longer parsed as active requirements; previously the header form reported `ID_REQUIREMENT_MISSING` and `SCENARIO_MISSING`.
- Stele verifies that removed behavior is gone: `SPEC_REMOVED_UNMATCHED` for a removed name that matches no current requirement, `PLAN_REMOVED_BEHAVIOR_PLANNED` for plan entries that still name it, and `LINK_REMOVED_BEHAVIOR_ANCHORED` for code and tests still anchored to it, in the change and, after archiving, in `--specs`.
- The init requirement "Initialize a consumer project" is now "Initialize a project", and its scenario `scn.init.754fd262e114` is titled "Initialize without a default change", matching its text. IDs and behavior are unchanged.
- Known limitation: an annotation line inside a fenced code block is still reported as `SPEC_ANNOTATION_MISPLACED`; a follow-up change makes the check fence-aware.

## 0.1.0-rc.3 — Release candidate

- **Breaking:** the report's top-level `verdict` is now the overall verdict, and reports have schema version `2.1` with `verdicts: {linkage, execution, overall}`. `overall` is `pass` only when linkage passes and the current evidence passed; missing or stale evidence makes it `incomplete`, and a failed test makes it `fail`. In the proposal stage it equals `linkage`. Read `verdicts.linkage` for the old meaning of `verdict`. `stele verify` still exits according to linkage, and its human output adds execution and overall lines. `stele validate --json` adds the same `verdicts`.
- Added `stele index`, which prints a deterministic JSON link index of requirements, scenarios, anchors, planned evidence with approval states, and last execution outcomes marked `stale` when inputs changed. With `--change` it also includes the current specifications, labelled by scope; `--output-file` writes it to a file. See the new [Link index](https://jensvansteen.github.io/stele/reference/link-index) reference.
- Requirements now keep their body text, and scenarios their raw text and `WHEN`/`THEN`/`AND` steps, including multi-line bullets, for editor hover cards.
- `stele test` accepts positional targets: requirement, scenario, and evidence IDs, and `spec.md` files. Targets combine, each test runs once, outcomes merge into the stored evidence without discarding others, and an unknown target exits with code `2` before any test runs.
- Added `--all` to `test`, `verify`, `validate`, and `index`, which checks the current specifications and every active change as separate scopes with one combined exit code (`2` over `1` over `0`).
- Added `--evidence-file` and `--report-file`. `--evidence` and `--report` still work until 0.2.0 and print a deprecation warning.
- Evidence files have schema version `3`: every execution records the `inputDigest` of its run, so each outcome can be marked stale on its own.
- TypeScript test names that are template literals with an interpolation no longer resolve to a selector, because they never selected the intended test by exact name. Such anchors now report `ANCHOR_TARGET_MISSING` and run as `target-not-resolved`.
- The `adapter` field of `stele.config.json` now selects the specification backend. `openspec` remains the only and default adapter; other values exit with code `2`. All commands reach OpenSpec through this adapter.
- `init`, `verify`, and `validate` warn when the project's OpenSpec skills or `stele` schema were generated by another OpenSpec version, and `init` warns when the `openspec` on `PATH` reports another version. The new `--strict-versions` flag turns these warnings into errors with exit code `1`.
- Documented the Stele model and the OpenSpec version policy, including the upgrade checklist.
- Added version 2 linkage plans. A plan now lists, per scenario, evidence entries with an evidence ID (`<scenario>.<level>[.<n>]`), a level, a rationale, an advisory placement, and an approval, and no code or test locations. `@verifies` anchors name evidence IDs, and verification reports `PLAN_EVIDENCE_MISSING`, `PLAN_EVIDENCE_INVALID`, `PLAN_UNKNOWN_ID`, `PLAN_UNAPPROVED`, `PLAN_APPROVAL_STALE`, `LINK_EVIDENCE_MISSING`, and `ANCHOR_EVIDENCE_UNPLANNED`.
- Added `stele approve`, which reviews entries in a terminal, approves them in bulk with `--all --yes`, or records a confirmation given in an agent conversation with `--confirmed-in-chat`. It refuses to approve anything otherwise.
- Added `stele plan migrate`, which converts version 1 plans to version 2 with unapproved entries.
- Version 1 plans still work until 0.2.0 and now produce a `PLAN_V1_DEPRECATED` warning. Warnings no longer mark the proposal stage as failed.
- Reports list planned evidence per scenario, links and test executions carry evidence IDs and levels, and a failed scenario names its failed evidence.
- The `stele-plan` skill now covers level definitions, rationales, advisory placement, the version 2 format, and the conversational approval step; the `stele` schema's plan template is a version 2 skeleton.
- Added `stele ids`, which inserts deterministic, collision-checked Verification-IDs into a change's delta specs. `--check` reports missing IDs for CI, and `--json` lists them.
- `stele init` now sets up OpenSpec when the project has none, using the bundled OpenSpec CLI (`--tools` chooses its tools), forks a `stele` workflow schema with a `verification` planning step, and merges Stele guidance into `openspec/config.yaml`. `--refresh-schema` re-forks the schema.
- `stele init` installs the `stele-propose`, `stele-apply`, and `stele-archive` skills as the default entry points, next to the rewritten `stele-plan` and `stele-verify` reference skills.
- `stele init --change` is now optional. Without a default change, `verify`, `test`, and `validate` need `--change` or `--specs`.
- `verify`, `test`, and `validate` now stop with exit code `2` when the selected change has no delta specs or `--specs` finds no current specifications. Previously `verify` passed with zero requirements.
- Linked Node tests no longer inherit `NODE_TEST_CONTEXT`, so Stele records them correctly when it runs inside `node --test`.

## 0.1.0-rc.2 — Release candidate

- **Breaking:** a linkage plan whose `changeId` names another change now fails with `PLAN_CHANGE_MISMATCH`. Store each change's plan in `openspec/changes/<change>/linkage-plan.json`.
- Added Go consumer support: anchors in Go comments resolve to functions, methods, types, and `TestXxx` functions, and linked Go tests run individually with `go test -json -count=1`, honoring `//go:build` tags. Skipped Go tests count as failed with reason `test-skipped`, and unparsable Go files stop verification.
- A scenario linked to several tests now passes only when every one of them passes; previously the last execution decided.
- The evidence digest now also covers `pkg/` and Go files in the repository root.
- Added `--specs` to `verify`, `test`, and `validate` to keep verifying behavior after `openspec archive`, using the combined plans of archived changes.
- Each change now reads its own `openspec/changes/<change>/linkage-plan.json`, falling back to `artifacts/linkage-plan.json`.
- Anchors for IDs declared by other changes or by the current specifications no longer count as `ANCHOR_DANGLING`.
- Stele now verifies its own behavior with Stele: the repository carries OpenSpec changes, linkage plans, and anchors for its CLI, Go support, TypeScript scanning, and verification scope.
- Fixed test anchors on `void test(...)` and `await test(...)` calls, the form used in the Build a Todo guide, which previously reported `ANCHOR_TARGET_MISSING`.
- TypeScript annotations are now read only from comments. Anchor text inside string and template literals no longer creates anchors.

## 0.1.0-rc.1 — Release candidate

- Reimplemented deterministic verification, anchor scanning, report generation, scenario execution, OpenSpec orchestration, initialization, and the CLI in Go.
- Packaged native macOS and Linux binaries for ARM64 and x64, selected at installation without a runtime Node launcher.
- Added exact named TypeScript test selection for v0.1 consumers, race-enabled tests for the Go verifier, a strict coverage gate, `golangci-lint`, and Linux/macOS GitHub Actions.
- Added repository-local planning and verification skills to the package initializer.
- Added a VitePress documentation site with guides, concepts, CLI and architecture reference, and examples.
- Kept a plain Todo showcase in the independent `stele-examples` consumer repository; the verification dashboard is deferred.
- Defined v0.1 consumer support as TypeScript-first; Go and other consumer languages remain future adapter work.

## Prototype history

- Proved the OpenSpec and stable-ID workflow with the original Todo showcase, dashboard, recordings, deterministic JavaScript verifier, and local npm tarball installation.
