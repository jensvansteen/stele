# Stele methodology

Spec-driven development where the spec is the source of truth, code fulfills it, and a guardrail engine refuses to ship code that disagrees with the spec.

Name from *stele* — an ancient inscribed stone tablet that recorded laws, decrees, and contracts. The spec is the stele; code is the work that lives under its authority.

> **Product scope:** This document preserves the broader Stele methodology and includes future designs. The v0.1 product supports TypeScript consumer source and tests only. Stele itself is implemented in Go; other consumer languages and polyglot projects require adapters that have not shipped yet.

## TL;DR

- **Specs live in the repo** under `docs/intent/`, `docs/spec/`, `docs/adr/`
- **Every requirement is a *claim*** — a stable, IDed statement of what the system does
- **Tests and code anchor to claims** by ID at the points they exercise or enforce them
- **A guardrail engine** (`stele verify`) blocks commits when claims aren't fulfilled or anchors are dangling
- **A periodic audit** (`stele audit`) catches code-first drift that verify can't see
- **Claims have lifecycle** (draft / active / deprecated / archived) and may declare dependencies, variants, and ownership
- **Adoption is gradual** — greenfield uses full strictness; brownfield uses diff-mode with per-path ratchets
- **Monorepos use per-package canons** + optional shared root canon; polyrepos federate via external contracts
- **Spec types** extend the format for API contracts, library interfaces, etc.
- **Specs are skimmable AND stakeholder-friendly** — table-first, Summary-first, with optional non-engineer rendering
- **Generated code is excluded** — anchors live in human-edited wrappers, never in generated files
- **External contributors** have a lenient path that surfaces violations without blocking
- **Changes are tracked inline** — each spec has a `## History` section; `CHANGELOG.md` at repo root for releases

## Vocabulary

| Term | Meaning |
|---|---|
| **claim** | A single stable, IDed requirement in a spec. The unit of the methodology. |
| **canon** | The set of all claims in a project (small *c*, like a body of accepted text). |
| **anchor** | A reference to a claim's ID in code or tests. A `// auth-2.1` comment is an anchor. |
| **fulfilled** | A claim is fulfilled when it has ≥1 test anchor *and* ≥1 code anchor. |
| **dangling** | An anchor that points to a claim ID the canon does not contain. |
| **guardrail** | The engine in `stele verify` that runs rules over the canon + anchors and gates commits. |
| **drift** | Spec and code falling out of agreement. Forward drift caught by verify; code-first drift caught by audit. |
| **baseline** | A git tag marking the point stele was adopted on a brownfield codebase. |
| **variant** | A flag-gated or experiment-gated context in which a claim applies. |

## The five phases

| Phase | Output | Driver |
|---|---|---|
| 1. Discovery | `docs/intent/vision.md`, `docs/intent/journeys.md` | User + agent Q&A |
| 2. Specification | `docs/spec/<capability>/spec.md` per capability | Agent drafts, user reviews |
| 3. Test scaffolding | Tests with anchors | Agent generates, user approves |
| 4. Implementation | Code with anchors at enforcement points | Agent against spec; user reviews |
| 5. Change management | Direct spec edits + History entries + diff-driven sync | User edits, agent applies implications |

### Single-repo, single-package

```
<project>/
├── docs/
│   ├── intent/
│   │   ├── vision.md
│   │   └── journeys.md
│   ├── spec/
│   │   ├── <capability>/

│   │   └── <area>/<capability>/spec.md # nested OK
│   ├── adr/
│   │   └── 0001-<slug>.md
│   └── .stele/
│       ├── config.toml
│       └── rules/                      # project-local custom rules
├── CONTRIBUTING.md                     # generated by stele-init
├── CHANGELOG.md
└── (source, tests)
```

Spec folders can be arbitrarily nested. The verify engine globs `docs/spec/**/spec.md`.

See dedicated sections below for monorepo (per-package canons) and polyrepo (cross-repo contracts) layouts.

## Intent docs: vision, journeys, and the tracker boundary

Specs and trackers (Linear / GitHub Issues / Jira) answer different questions. Confusing them produces both bloated specs and stale tickets.

| | **Journeys** (`docs/intent/journeys.md`) | **Tracker issues** |
|---|---|---|
| Answers | "How does a real user use this product?" | "What needs to be done next?" |
| Timeframe | Stable — months/years | Short — days/weeks |
| Count | 3–5 total per project | Hundreds over a project's life |
| Read by | Anyone joining the project | The team this sprint |
| Lifecycle | Edited rarely (major product shifts) | Created, closed, archived constantly |
| Linked to | Claims that fulfill them | Claims being added/modified by this work |

**Bridge rule:** every tracker issue references the claims it implements or modifies (e.g. *"Implements `auth-2.1`, `auth-2.2`"* in the issue body). When the issue closes, those claims should be fulfilled — verifiable via `stele verify`.

## Specs for non-engineers

Stele specs need to be readable by people who don't write code — PMs, designers, security reviewers, compliance officers, exec stakeholders. The methodology already optimizes for this (table-first, plain English in Trigger/Behavior), but a few conventions make stakeholder review smooth.

### Conventions

- **Every spec starts with a Purpose** — 1–3 plain-English sentences. A non-engineer should understand the spec's intent from this section alone.
- **The Claims table is skimmable** — Trigger and Behavior columns are plain English; non-engineers can ignore the ID column.
- **Verification and Boundaries can be skipped** — they're for engineers and reviewers. Non-engineers skim Purpose + Claims and move on.
- **`docs/intent/journeys.md` is the natural entry point** — non-engineers should start here. It's the product narrative; specs are the implementation contract.

### Stakeholder-friendly rendering (future)

`stele render --audience=stakeholder` (planned) strips engineering sections (Verification, Boundaries, History), simplifies tables, and produces a clean docs-site view for PMs/designers/reviewers. The same canon, different presentation.

Until that ships, point non-engineers at journeys.md and Purpose sections.

## Claim IDs

Stable identifiers that link spec → test → code. Three rules:

1. **Format:** `<prefix>-<n>[.<m>...]`. Prefix is lowercase by default; uppercase accepted. Hierarchical via dots: `auth-1`, `auth-1.2`, `auth-1.2.1`.
2. **Stability:** Never renumber. Removed claims are *deprecated in place*, not deleted.
3. **Anchoring:** The same ID appears in the spec heading, in at least one test anchor, and in code at the enforcement point.

### Example trace (TypeScript)

In `docs/spec/auth/login/spec.md`:
```markdown
### auth-2.1: Reject expired tokens
- **Trigger:** request arrives with token whose `exp` is in the past
- **Behavior:** respond `401 Unauthorized` with code `TOKEN_EXPIRED`
- **Output:** JSON `{ error: "TOKEN_EXPIRED", expiredAt }`
```

```ts
// tests/auth.test.ts
test("auth-2.1: rejects expired tokens with 401 TOKEN_EXPIRED", async () => {
  const expired = signToken({ exp: nowSeconds() - 60 });
  const res = await api.get("/me", { token: expired });
  expect(res.status).toBe(401);
  expect(res.body.error).toBe("TOKEN_EXPIRED");
});
```

```ts
// src/middleware/auth.ts
export function authenticate(req, res, next) {
  const token = parseToken(req);
  // auth-2.1
  if (token.exp < nowSeconds()) {
    return res.status(401).json({ error: "TOKEN_EXPIRED", expiredAt: token.exp });
  }
  next();
}
```

### Claim metadata (optional columns/fields)

Claims can declare additional metadata via extra Claims-table columns or sub-bullets:

| Field | Purpose | Example |
|---|---|---|
| `Requires` | Other claims this one depends on | `cart-3.1` requires `inventory-1.2`, `auth-1.4` |
| `Applies when` | Variant gating (feature flag, A/B arm) | `checkout-5.2` applies when `flag:one-click-checkout` |
| `Status` | Per-claim lifecycle (overrides spec-level) | `auth-2.4` is deprecated, replaced by `auth-2.7` |

These are all optional. Trivial specs skip them; complex ones lean on them.

### Cross-claim dependencies

When a claim depends on another, declare it. Two forms:

**Table column form (for many claims):**

| ID | Title | Trigger | Behavior | Requires |
|---|---|---|---|---|
| cart-3.1 | Validate stock at checkout | checkout starts | check inventory for each cart item | `inventory-1.2`, `auth-1.4` |
| cart-3.2 | Reserve stock briefly | cart-3.1 succeeds | hold inventory 5 min | `cart-3.1` |

**Sub-bullet form (for occasional deps):**

```markdown
### cart-3.1: Validate stock at checkout
- **Trigger:** checkout starts
- **Behavior:** check inventory for each cart item
- **Requires:** `inventory-1.2`, `auth-1.4`
```

The guardrail rule `dependency-coherence` (warn) checks:
- Every required claim exists in the canon (no dangling deps)
- If a required claim is `deprecated` or `archived`, the requiring claim should be too (otherwise warn)
- Cyclic deps are warned but not blocked

### Feature flags and A/B variants

Real products have variants. A claim might apply only when a feature flag is on, or only in one arm of an experiment.

Declare with `Applies when`:

| ID | Title | Trigger | Behavior | Applies when |
|---|---|---|---|---|
| checkout-5.1 | Standard checkout | user has any payment method | walk through pay form | `always` (default — omit column) |
| checkout-5.2 | One-click pay | user has card on file | render one-click button | `flag:one-click-checkout` |
| checkout-5.3 | Crypto pay (treatment) | user opts in | show crypto options | `variant:checkout-experiment-2026:crypto` |

Values:
- `always` — default; omit the column entirely if all claims apply universally
- `flag:<name>` — applies only when the named flag is enabled
- `variant:<experiment>:<arm>` — applies only in the named experiment arm
- Multiple values comma-separated: `flag:a,flag:b` (any), `flag:a & flag:b` (all)

In tests, the test name or annotation echoes the variant:

```ts
test("checkout-5.2 [flag:one-click-checkout]: renders one-click button when card on file", ...);
```

The guardrail rule `variant-coverage` (warn) checks: for each variant declared in `docs/.stele/config.toml`, every claim that applies in that variant has at least one test anchor exercising it under that variant.

```toml
# docs/.stele/config.toml
[variants]
known_flags = ["one-click-checkout", "new-cart-ui"]
known_experiments = [
  { name = "checkout-experiment-2026", arms = ["control", "crypto"] }
]
```

`stele audit` reports variant coverage as part of the matrix.

## Spec types

Specs declare their type in frontmatter. Different types share most of the methodology but extend it with type-specific sections and rules.

| Type | For | Adds | Type-specific rules |
|---|---|---|---|
| `capability` (default) | Behavior of a product feature | Standard claim+scenario shape | claim-fulfillment (default) |
| `api-contract` | HTTP/gRPC endpoint behavior | `Source` section linking to OpenAPI/proto | schema-conformance, endpoint-anchor, schema-drift, external-contract-resolves |
| `library-interface` | Library/SDK/component public API | Per-export claims, API stability section | library-export-coverage, library-signature-match, library-stability |
| `data-model` (planned) | Persistent schema + invariants | Schema + migrations sections | TBD |
| `workflow` (planned) | Multi-step async process | State machine + transitions | TBD |

The default type is `capability` — no frontmatter required.

### Capability spec (default)

The default. See "Spec file shape" below.

### api-contract spec

For HTTP/gRPC endpoints where OpenAPI or proto is already the source of truth for *shape*. The spec adds *behavior*.

```markdown
---
type: api-contract
schema: openapi.yaml#/paths/~1auth~1login/post
---

# API Contract: POST /auth/login

## Source
- **OpenAPI:** `openapi.yaml#/paths/~1auth~1login/post`
- **Generated types:** `src/generated/auth.ts:LoginResponse`

## Purpose
Authenticate a user with email + password. Issue access + refresh tokens.

## Claims
| ID | Title | Trigger | Behavior |
|---|---|---|---|
| login-1 | Valid credentials → tokens | email + password match | issue access + refresh tokens, 200 OK |
| login-1.1 | Response conforms to schema | login-1 satisfied | validates against LoginResponse schema |
| login-2 | Invalid credentials → 401 | email/password mismatch | 401 with code `INVALID_CREDENTIALS` |
| login-3 | Rate limit | >5 attempts/min same IP | 429 `RATE_LIMITED`, retry-after header |
| login-4 | Successful login emits event | login-1 satisfied | publish `user.logged_in` to event bus |
```

For cross-repo contracts (service A consuming service B's API), see "Polyrepo and cross-repo contracts" below.

### library-interface spec

For libraries (internal packages or published OSS) where the public API IS the spec.

```markdown
---
type: library-interface
source: [src/index.ts, types/index.d.ts]
exports:
  - name: parseDate
    signature: "(input: string, format?: string) => Date | null"
  - name: formatDate
    signature: "(date: Date, format: string) => string"
stability: stable
---

# Library: @myorg/date-utils

## Purpose
Parsing and formatting dates without timezone dependencies.

## Claims

### parseDate
| ID | Title | Trigger | Behavior |
|---|---|---|---|
| parse-1 | Parse ISO 8601 | input matches ISO 8601 | return Date in UTC |
| parse-1.1 | Return null on invalid | input not parseable | return null (do not throw) |

### formatDate
| ID | Title | Trigger | Behavior |
|---|---|---|---|
| format-1 | Apply format string | valid Date + format | return string per format |

## API stability
- **Status:** Stable
- **Semver promise:** Patch preserves claims; minor may add; major may modify/deprecate
```

Type-specific rules: `library-export-coverage`, `library-signature-match`, `library-stability`.

Works for UI component libraries too — each component is an export with claims about props, states, accessibility.

## Spec lifecycle

Specs (and individual claims) have a lifecycle. Declare via frontmatter for spec-level; via the `Status` column for claim-level overrides.

### Status values

| Status | Meaning | Verify behavior |
|---|---|---|
| `draft` | Spec being written; not yet enforced | claim-fulfillment runs in `warn` mode |
| `active` (default) | Fully enforced | All rules apply normally |
| `deprecated` | Kept for reference; no new code should anchor here | claim-fulfillment downgrades to `warn`; new anchors warn |
| `archived` | Retired capability | Spec excluded from verify entirely |

### Spec-level (frontmatter)

```markdown
---
type: capability
status: deprecated
deprecated_in: "2026-08-01"
replaced_by: docs/spec/checkout/payment-v2/spec.md
---

# Capability: Payment (legacy)
...
```

For `archived`:

```markdown
---
type: capability
status: archived
archived_in: "v2.0.0"
archived_reason: "Capability removed in the 2026 redesign"
---
```

Archived specs are kept in `docs/spec/` for historical reference but excluded from verify. Move them to `docs/spec/_archive/<...>/spec.md` if you want them out of the main browse path.

### Claim-level (Status column)

Individual claims within an active spec can be deprecated:

| ID | Title | Trigger | Behavior | Status |
|---|---|---|---|---|
| auth-2.4 | Token refresh via legacy endpoint | refresh request | exchange refresh token | deprecated, replaced by `auth-2.7` |
| auth-2.7 | Token refresh via /auth/refresh | refresh request | exchange refresh token, rotate | active (default) |

### Guardrail rule

`lifecycle-coherence` (warn):
- An `active` claim must not `Require` a `deprecated` or `archived` claim
- A `deprecated` claim should have a `replaced_by` pointer
- Anchors in active code referencing deprecated claims surface as warnings (use the replacement)

### Promoting a spec from `draft` to `active`

A spec only leaves `draft` once it's ready to govern code. Concretely:

- Every claim has a stable ID, a Trigger, and a Behavior.
- The `Open questions` section is empty or removed.
- Verification table is filled for every claim.
- Boundaries are written (at least the 🚫 line; ✅ and ⚠️ if they apply).

Implementation does not start while questions are open. If a claim depends on an unresolved decision, either resolve it first or split the claim into a deferred sub-spec that stays `draft`. Code anchored to a `draft` claim is the same as no anchor at all (`claim-fulfillment` is `warn`, not `fail`, for draft specs — but the moment the spec goes active the bar moves to `fail`).

### Lifecycle anti-patterns

- **Renaming an active spec to `archived` to make verify pass.** That's hiding the problem; the work didn't go away.
- **Leaving `draft` specs forever.** Draft is for *active drafting* (a few days/weeks). After that, either ship as active or archive.
- **Promoting a spec to `active` with unresolved Open questions.** The unknowns will harden into accidental contract. Resolve, defer, or split — but don't promote with them present.
- **Starting implementation against a `draft` spec.** The spec isn't load-bearing until it's active. If you're writing code that needs to be anchored, the spec needs to be ready.

## Spec file shape

Every spec follows this skeleton (capability default; other types extend). Aim for skimmable — table-first.

```markdown
---
# Optional frontmatter; omit for the default `capability` type at `active` status
type: capability
status: active
---

# Capability: <human-readable name>

## Purpose
<1–3 sentences. What this capability does, who consumes it. Readable by non-engineers.>

## Claims

| ID | Title | Trigger | Behavior |
|---|---|---|---|
| prefix-1 | <title> | <when> | <what happens> |
| prefix-1.1 | <title> | <when> | <what happens> |
| prefix-2 | <title> | <when> | <what happens> |

(Optional columns: `Requires`, `Applies when`, `Status` — add per-need)

Claims are **defined in the table**, not in headings. The table is the canon; the default `claim_pattern` regex scans table rows. A `### claim-1.1` heading is permitted only as a label above a nuance/rationale block — it must echo an ID already declared in the table, not introduce a new one.

### Nuance / rationale
<Only when a claim needs more than the table cell allows. The heading must echo an ID already in the Claims table.>

## Scenarios

### <scenario name> [prefix-1, prefix-1.1]
<Pick the lightest format that fits.>

## Verification

| Claim | Scope | Character | Cost |
|---|---|---|---|
| prefix-1 | integration | example | fast |

## Boundaries

- ✅ **Always do:** <hard rule>
- ⚠️ **Ask first:** <high-impact action>
- 🚫 **Never do:** <hard stop>

## Non-goals
- <Thing this spec explicitly does NOT do>

## Open questions
<Optional. Use only while the spec is `status: draft`. Must be empty or absent before promoting to `active`.>
- <unresolved question, with the spec or capability that will close it>

## History
- YYYY-MM-DD — Spec created
- YYYY-MM-DD — Added prefix-N.M (commit <sha>)
```

### Scenario formats — pick the lightest that fits

| Format | When |
|---|---|
| Inline single-sentence GWT | Trivial scenarios |
| Numbered steps | Sequential flows |
| Full GWT block | ≥2 preconditions, branching outcomes |

## Test type rubric (Verification table)

### Scope (primary)
- `unit` — pure function or single class, no I/O
- `integration` — multiple components, possibly file system or process
- `e2e` — full app or CLI flow end-to-end

### Character

| Character | Use when | TypeScript example |
|---|---|---|
| `example` | 99% of cases | `expect(add(2, 3)).toBe(5)` |
| `property` | Invariants over generated inputs | `fc.assert(fc.property(fc.string(), s => parse(serialize(s)) === s))` |
| `snapshot` | Generated config, API response | `expect(renderConfig(opts)).toMatchSnapshot()` |
| `contract` | Subsystem boundary | `pact.between("api", "billing").expects(...)` |
| `regression` | A specific bug must never return | `test("bug #4127: empty cart did not throw", ...)` |
| `performance` | Latency/memory budget | `expect(latencyMs).toBeLessThan(100)` |
| `stress` | Concurrency, load, races | 1000 parallel writes; assert no lost updates |
| `visual-regression` | UI rendering stable | Percy / Chromatic diff |
| `a11y` | Keyboard nav, contrast, ARIA | `expect(component).toHaveNoViolations()` |

### Cost flags (project-extensible)
- **Speed:** `fast` / `slow` / `very-slow`
- **Determinism:** `flaky-risk`
- **Environment:** `needs-<resource>` — projects define their own

## Three-tier boundaries

- **✅ Always do** — actions the agent takes without asking
- **⚠️ Ask first** — actions with broad impact
- **🚫 Never do** — hard stops

## The guardrail (`stele verify`)

| Rule | What it checks | Severity |
|---|---|---|
| `claim-fulfillment` | Every active claim has ≥1 test anchor and ≥1 code anchor | fail |
| `no-dangling-anchors` | Every anchor in code/tests resolves to a real claim | fail |
| `spec-shape` | Each `spec.md` has required sections | fail |
| `no-open-questions-in-active` | An `active` spec has no non-empty `## Open questions` section | fail |
| `claim-stability` | No claim ID has been silently renumbered | warn |
| `history-consistency` | Substantive spec edits have a History entry | warn |
| `boundaries-respected` | No code modifies paths/files marked 🚫 in any spec | warn |
| `dependency-coherence` | All `Requires` resolve; no active claim requires deprecated/archived | warn |
| `lifecycle-coherence` | Status transitions are coherent (no active depends on archived, etc.) | warn |
| `variant-coverage` | Every claim's variants have test anchors exercising them | warn |

Type-specific rules (api-contract, library-interface) load when a spec's frontmatter declares that type.

`stele verify --pre-commit` runs only `fail`-severity for speed.
`stele verify --strict` promotes all warnings to fails.
`stele verify --lenient` runs everything but exits 0 on legacy violations — used for external-contributor PRs (see below).

## The audit loop (`stele audit`)

> **Roadmap:** Language-specific audit adapters are a future capability. The v0.1 consumer path performs TypeScript anchor and exact-test verification.

Verify catches scaffolding drift; audit catches code-first drift (new functionality without specs).

|  | `stele verify` | `stele audit` |
|---|---|---|
| Cadence | Every commit | Weekly cron / release / nightly |
| Speed budget | Sub-second | Minutes acceptable |
| Catches | Scaffolding drift | Code-first drift |
| Implementation | Regex + grep | Language-specific parsers |

A future audit command would walk the project's public surface through per-language adapters, find anchors, and report:
- New public items added since `--since` without anchors
- Files with low anchor density
- Endpoints without `api-contract` specs
- Variant coverage gaps

Run periodically in CI. In `--strict`, fails the build on drift. Default is warn-only.

The planned configuration is per package in `docs/.stele/config.toml` (`[audit] adapters = [...]`). Polyglot packages would list multiple adapters and merge their results into one report. See "Polyglot packages" under Monorepos for the proposed pattern.

## Adoption modes: greenfield vs brownfield

### Greenfield
Full strictness from day one. `stele verify` runs whole-canon mode. Default for `stele init` on a fresh repo.

### Brownfield
"Spec what you touch" (OpenSpec philosophy). Don't backfill. Diff-mode verify; baseline tag (`stele-baseline-v0`) marks the grandfathered line. Per-path strictness via `docs/.stele/config.toml`:

```toml
[mode]
default = "diff"
baseline_ref = "stele-baseline-v0"

[strictness]
"src/legacy/**" = "off"
"src/billing/**" = "warn"
"src/auth/**" = "fail"
"src/**" = "warn"
```

Strictness ratchets one direction: `off` → `warn` → `fail`.

The `/stele-onboard` skill (planned) reverse-engineers initial specs from existing code, creates the baseline, and writes the config with sensible defaults.

### Brownfield anti-patterns
- Bulk backfilling specs for existing code
- Stuck at `warn` forever — the ratchet is supposed to ratchet
- Adopting `fail` everywhere on day one

## Monorepos and workspaces

One canon per package + optional shared root canon. Workspace config at `docs/.stele/workspace.toml`:

```toml
[workspace]
packages = ["packages/api", "packages/web", "packages/shared"]
detect_from = "pnpm-workspace.yaml"   # or turbo.json, nx.json, etc.
root_canon = "docs/spec"

[cross_package_refs]
enabled = true
on_prefix_collision = "error"
```

### Verify modes
- `stele verify` (in package dir) — package only
- `stele verify --all` — every package, aggregated
- `stele verify --affected --since main` — only diffed packages

### Cross-surface products (frontend + backend + mobile)

A common shape. Layered canon: shared/ owns platform-independent domain rules; per-package canons own surface-specific behavior.

```
my-product/
├── docs/spec/shared/{auth,cart,checkout}/spec.md    # platform-independent
├── packages/
│   ├── backend/docs/spec/api/.../spec.md            # type: api-contract
│   ├── web/docs/spec/ui/.../spec.md
│   ├── mobile/docs/spec/flows/.../spec.md
│   └── shared/docs/spec/types/spec.md
```

Cross-surface journeys reference claims across packages. Anchors flow naturally — a shared rule like `shared-cart-1.2` is anchored from backend, web, and mobile code.

### Polyglot packages (future)

A future adapter model can support packages that contain multiple languages — an Electron app with a TypeScript renderer and Rust or C++ native modules, a Tauri app with a TypeScript frontend and Rust core, or a Python data package with a TypeScript dashboard.

This is distinct from a multi-language SDK repository, where each language lives in its own package. The polyglot case is when **one logical package** (one deployable, one CI pipeline, one team) mixes languages internally.

After those adapters ship, a package could configure multiple audit adapters in its `docs/.stele/config.toml`:

```toml
# packages/electron-app/docs/.stele/config.toml
[audit]
adapters = ["typescript", "rust"]   # both run; results merged into one report

# Or with explicit path scoping when the language boundary is clean:
[audit.adapters]
typescript = "src/renderer/**"
rust = "src-native/**"
```

Each future adapter would parse its own file types and emit normalized drift signals for one aggregate report. The stable claim identity would remain shared across languages, while each adapter would define how declarations and exact tests are resolved.

The claim itself is single-source: one `claim-X.Y` in one spec, anchored from any language in any file of the package.

## Polyrepo and cross-repo contracts

Distinct from monorepo. Each repo has its own canon. Cross-repo coordination happens through **contracts**, not through a federated canon.

### Pattern

Each service's API is an `api-contract` spec in that service's repo. Consumer services reference it via external schema URL:

```markdown
---
type: api-contract
external_contract: "https://github.com/myorg/auth-service/raw/v1.4.0/openapi.yaml#/paths/~1auth~1validate/post"
external_contract_ref: "v1.4.0"
---

# API Contract: AuthService validate (consumed)

## Purpose
The cart-service calls AuthService.validate to confirm a session.

## Claims
| ID | Title | Trigger | Behavior |
|---|---|---|---|
| auth-consume-1 | Validate request | session token from cart request | call AuthService.validate, handle response |
| auth-consume-1.1 | Surface 401 to client | AuthService returns 401 | propagate as 401 to caller |
| auth-consume-1.2 | Cache successful validation | 200 from AuthService | cache 30s, key on token |
```

### Guardrail rule

`external-contract-resolves` (warn):
- Fetch the URL at verify time (or use a cached snapshot)
- Confirm the path/operation exists in the linked schema
- Compare local expectations to schema; surface drift

### Contract pact tests

Use the `contract` test character. Tools like Pact, Schemathesis, or Postman recordings verify the consumer's expectations against the provider's actual API.

### What stele does NOT do for polyrepo

- **Federate canons across repos.** That's an organizational concern (service catalog, schema registry, API mesh). Stele's job is to make each service's contracts and expectations visible.
- **Run cross-repo verify.** Each repo's `stele verify` checks its own canon plus its external-contract resolutions.

For tight polyrepo coordination, a separate aggregator service can pull canon manifests from each repo and produce a cross-service dashboard. Stele doesn't prescribe one.

## External contributors

Open source projects and any repo accepting outside PRs need a path for contributors who don't have stele installed and don't know the conventions.

### `CONTRIBUTING.md` template

`stele init` generates a `CONTRIBUTING.md` covering:
- This project uses stele; specs live in `docs/`
- Conventions: claim IDs in spec headings, anchors in code/tests
- For PRs touching specs: explain the change; the team will append a History entry on merge
- For PRs adding code under a strict path: include or reference a claim; maintainers can help

### `--lenient` PR mode

For external contributor PRs, CI runs `stele verify --lenient`:

- Existing violations from before the PR are reported but don't fail the build
- New violations introduced by the PR are reported and surfaced as PR comments
- Build doesn't block (so contributors aren't gated by tooling they don't have)
- Maintainers fix up the spec/anchors in a follow-up commit before merge

Configure in `docs/.stele/config.toml`:

```toml
[contrib]
lenient_for_authors = ["external", "first-time-contributor"]   # via GitHub bot labels
fail_on_new_violations = true   # but warn on legacy ones
```

For internal team PRs, the default strict pre-commit + CI behavior applies.

### Anti-pattern

Making external contributors install stele to contribute. Stele is for the maintainers; contributors should feel friction-free except where they're knowingly changing a contract.

## Spec ownership (CODEOWNERS)

Stele doesn't reinvent ownership; it leverages `CODEOWNERS` files. Place a `CODEOWNERS` file inside any `docs/spec/<area>/` directory:

```
# docs/spec/auth/CODEOWNERS
* @myorg/auth-team
spec.md @alice @auth-lead
```

GitHub/GitLab automatically request reviews from the listed owners when those files change. Stele integrates by:

- **Discovery**: when an agent proposes a change to a spec, it reads any `CODEOWNERS` in the path and surfaces "this change needs review from @owners"
- **No enforcement**: stele doesn't block merges based on CODEOWNERS — that's the platform's job (GitHub branch protection, GitLab approval rules)
- **Audit visibility**: `stele audit --owners` lists which capabilities have explicit owners and which don't

This is a soft methodology recommendation, not a guardrail rule. For big orgs it's load-bearing; for solo projects it's noise.

## Generated code patterns

Anchors must NOT live in generated files — they'll be clobbered on regen. The pattern is to anchor in human-edited wrappers around generated code.

### Anti-pattern: anchors in generated files

```ts
// src/generated/auth_pb.ts  — DO NOT do this
export class LoginRequest {
  // auth-2.1   ← will be lost on next protoc run
  constructor(...) { ... }
}
```

### Pattern: anchors in the wrapper

```ts
// src/auth/login-handler.ts  — DO this
import { LoginRequest } from "../generated/auth_pb";

export async function handleLogin(req: LoginRequest) {
  // auth-2.1
  if (await tokenIsExpired(req.token)) {
    return { error: "TOKEN_EXPIRED", expiredAt: req.token.exp };
  }
  // ...
}
```

### Exclude generated paths from verify

```toml
# docs/.stele/config.toml
[strictness]
"src/generated/**" = "off"
"src/proto/**" = "off"
"**/*.gen.ts" = "off"
"**/*.generated.tsx" = "off"
```

`off` means the engine skips these files for anchor scanning AND for audit's public-surface analysis. Generated code is not part of the spec story.

### When the generated code IS the public surface

For SDK libraries where the published thing is generated from a schema, write a `library-interface` spec for the generated package. Claims describe the *behavior* the published SDK guarantees; the generated types describe the *shape*. Anchors live in non-generated wrapper/extension files.

## Change management

Lightweight. Three surfaces:

- **Per-spec `## History` section** — substantive edits append a line
- **Top-level `CHANGELOG.md`** — releases and breaking changes
- **`stele diff` + `/stele-sync`** (v1.5, planned) — propagate spec edits to code/tests

### What counts as substantive

| Edit | Treatment |
|---|---|
| Typo, formatting | git log only |
| Add/remove/deprecate a claim | History entry |
| Change Trigger/Behavior on existing claim | History entry |
| Change Boundaries or Status | History entry |
| Release / breaking change | `CHANGELOG.md` entry |

### Where to record what

| Change scope | Where |
|---|---|
| Trivial | git log only |
| Substantive single-spec | History entry |
| Multiple specs, related | History per affected spec + an ADR for the cross-cutting decision |
| Release / breaking | `CHANGELOG.md` |
| Long multi-month initiative with formal proposals | Project may introduce `docs/changes/` — not in default |

## Anti-patterns

- **UI nail-polish in specs.** Behavior contracts only.
- **Implementation hints as requirements.** Claims say *what*; algorithms live in code or ADRs.
- **Auto-generated specs the user has not read.** Hallucination with a header.
- **Wishful future features.** Goes in Non-goals.
- **Renumbered claim IDs.** Once present, permanent. Deprecate; do not reuse.
- **Prose where a table works.** Specs degrade as text gets longer.
- **"Tests later."** Unfulfilled claim = `stele verify` fails the next commit.
- **Sprinting through Discovery.** Vague answers in Phase 1 cause vague specs in Phase 2.
- **Bulk backfilling on brownfield.** Spec what you touch.
- **Adopting `fail` everywhere on day one of brownfield.** Kills momentum.
- **Stuck-at-warn ratchet.** Strictness is supposed to ratchet up; schedule reviews.
- **Single canon across a monorepo.** Per-package canons + optional shared root.
- **Anchors in generated files.** Anchors in wrappers, never in generated code.
- **Federated cross-repo canon.** Polyrepo coordinates via contracts, not via a shared canon.
- **Renaming an active spec to `archived` to make verify pass.** Hides the problem.
- **Leaving `draft` specs forever.** Ship or archive within weeks.
- **Promoting a spec to `active` with unresolved Open questions.** Unknowns harden into accidental contract.
- **Starting implementation against a `draft` spec.** The spec isn't load-bearing until active.
- **Forcing external contributors to install stele.** Use `--lenient` mode.
