## Why

Stele currently builds on OpenSpec (MIT, Fission AI). User workflows should attach to Stele's own concepts and entry points, so that the specification backend could later be forked or replaced without changing how people work.

Today the `adapter` field in `stele.config.json` is written by `stele init` but never read. OpenSpec-specific paths, parsing, and validation are spread through the verifier.

The OpenSpec version is pinned on purpose, through the exact `@fission-ai/openspec` dependency and the `OpenSpecVersion` constant. But nothing warns when a project's OpenSpec skills or Stele schema were generated by another OpenSpec version, or when a different `openspec` binary is on `PATH`. An OpenSpec update could then silently change how Stele works.

## What Changes

- **The adapter becomes a real seam.** The `adapter` setting selects a specification backend behind an internal interface. The interface covers:
  - where a change's or the current specifications live;
  - parsing identities from them;
  - locating plans and archived changes;
  - strict validation;
  - installing backend artifacts (skills, schema, configuration).

  `openspec` is the only implementation and the default. Unknown adapters are rejected.
- **Version drift warnings.** Stele warns when the project's OpenSpec skills, or its Stele schema fork, were generated by an OpenSpec version other than the pinned one. `stele init` also warns when the `openspec` on `PATH` reports another version. Warnings never change exit codes. The optional `--strict-versions` flag turns the drift into an error for teams that want CI to fail on it.
- **Documentation.**
  - A concepts page defines Stele's own model: the behavior spec with IDs, the evidence plan with approvals, anchors, evidence, and the index. OpenSpec is named as the current backend, with the credit "Stele currently builds on OpenSpec (MIT, Fission AI)".
  - A version policy page explains the deliberate pin, and makes an OpenSpec bump a Stele release step. The skills, schema, and lifecycle skills are re-checked in that step.

## Capabilities

### New Capabilities

- `backend`: selecting the specification backend and warning about backend version drift.

## Impact

- `internal/stele`: a new `adapter.go` with the backend interface and the OpenSpec implementation. The existing OpenSpec-specific code in `specs.go`, `scope.go`, `openspec.go`, and later `workflowschema.go` moves behind it without behavior changes. Drift checks are added to `init`, `verify`, and `validate`.
- Documentation covers concepts, version policy, CONTRIBUTING's release steps, and the changelog.
- It can land independently of `authoring-workflow` and `verification-strategy`, and before `link-index`, so the index is built on the adapter.
