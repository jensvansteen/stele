## Purpose

Keep Stele's workflow independent of its current specification backend, and make backend version changes visible instead of silent.

## ADDED Requirements

### Requirement: Select the specification backend
Verification-ID: req.backend.b5ff52883615

Stele SHALL resolve the specification backend from the `adapter` field of `stele.config.json`, defaulting to `openspec` when the field or file is absent. Every command SHALL use the selected backend to locate, parse, validate, and install backend-specific files. An adapter name that Stele does not support SHALL be rejected with exit code `2`.

#### Scenario: Use OpenSpec by default
Verification-ID: scn.backend.17bc5c526b79

- **WHEN** a project has no `stele.config.json`, or its `adapter` field is empty or `openspec`
- **THEN** Stele uses the OpenSpec backend and behaves as before

#### Scenario: Reject an unknown adapter
Verification-ID: scn.backend.e20f52b594b9

- **WHEN** `stele.config.json` names an adapter that Stele does not support
- **THEN** every command that reads the configuration exits with code `2` and lists the supported adapters

#### Scenario: Route commands through the backend
Verification-ID: scn.backend.ad74565b613f

- **WHEN** a test backend is selected that serves specifications from memory
- **THEN** `stele verify`, `stele test`, `stele validate`, and `stele ids` read identities and scopes only through that backend

### Requirement: Warn about backend version drift
Verification-ID: req.backend.17e80d964275

Stele SHALL warn, without changing its exit code, when files that the pinned OpenSpec version generates were generated by another version. This covers the project's OpenSpec skills (`metadata.generatedBy`) and the Stele schema fork. During `stele init`, Stele SHALL also warn when the `openspec` found on `PATH` reports a version other than the pinned one. With the optional `--strict-versions` flag, `stele init`, `stele verify`, and `stele validate` SHALL report the same drift as errors and exit with code `1`.

#### Scenario: Warn about skills from another OpenSpec version
Verification-ID: scn.backend.c077e67d1e58

- **WHEN** a project's OpenSpec skills record `generatedBy` 1.14.0 while Stele pins 1.13.0
- **THEN** `stele verify` prints a warning naming both versions and how to realign them, and its exit code is unchanged

#### Scenario: Warn about another openspec on PATH
Verification-ID: scn.backend.124f95bf55a3

- **WHEN** `stele init` runs and the `openspec` on `PATH` reports a version other than the pinned one
- **THEN** it warns that Stele uses its bundled OpenSpec 1.13.0 and names the version it found

#### Scenario: Fail on drift when strict versions are requested
Verification-ID: scn.backend.08f190c98ed9

- **WHEN** `stele verify --strict-versions` runs in a project whose OpenSpec skills record another OpenSpec version
- **THEN** it reports the drift as an error and exits with code `1`, while the same run without the flag only warns

#### Scenario: Stay silent when versions match
Verification-ID: scn.backend.0ee7b914816a

- **WHEN** the project's OpenSpec skills and schema fork match the pinned version, and no other `openspec` is on `PATH`
- **THEN** no drift warning is printed
